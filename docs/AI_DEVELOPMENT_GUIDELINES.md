## 2. GUI 아키텍처: UI와 로직의 완전한 이원화
- UI 코드는 오직 **"화면을 그리는 것"**과 **"이벤트 신호를 emit하는 것"**만 담당한다. 비즈니스 로직/계산/통신 코드를 UI 코드에 직접 섞지 마라.
- CPU-bound 작업과 IO-bound 작업을 구분하고, IO-bound 작업(네트워크 요청, 파일 다운로드, 프로세스 대기 등)이 메인(UI) 스레드를 점유하지 않도록 반드시 비동기/스레드로 분리하라.
- UI는 매 루프 주기마다:
  1. 쌓인 이벤트를 확인
  2. 처리/반영
  3. 화면 새로고침(refresh) 하는 구조를 따르라.

---

## 3. 비동기/병렬 처리 + 상태 머신
- 대기 시간(wait time)이 발생하는 작업은 기본적으로 비동기 또는 병렬화를 검토하라.
- 백그라운드 작업을 도입할 때는 반드시 그 작업을 감시하는 **상태 머신**을 함께 설계하라. 상태는 최소한 다음을 포함해 명시적으로 정의하라:
  - 시작 전 / 진행 중 / 완료 / 실패 (필요 시 취소 상태도 포함)
- 상태 전이는 **signal-slot(이벤트) 패턴**으로 통제하라: 특정 입력/조건이 발생했을 때만 신호를 emit하고, UI는 그 신호만 구독해서 반응하도록 하라. UI가 백그라운드 작업의 내부 상태를 직접 poll하게 만들지 마라.
- 정의되지 않은 상태 전이(예: "설치 중"에 취소 버튼을 누른 경우)가 없는지 스스로 점검하라.

## 4. AI(자기 자신) 사용에 대한 자기 검열
- 테스트를 통과시키기 위해 조건을 느슨하게 만들거나, 실패해야 할 케이스를 우회하는 **"가짜 성공(모킹 악용)"** 테스트를 작성하지 마라.
- 외부 API를 모킹할 때는 실제 응답 스키마(필드명, 타입, nullable 여부 등)를 정확히 재현하라. 모킹 데이터가 실제 서비스 스펙과 다르면 반드시 그 사실을 사용자에게 알려라.
- 기능을 구현한 뒤에는 스스로에게 *"GUI 프로그램에서 흔히 발생하는 실수/버그가 이 코드에 있는가?"*를 질문하고, 그 답을 검증하는 테스트를 함께 작성하라.

## 5. 표준 작업 파이프라인

### A. 신규 기능 개발
1. **티켓 구체화** — 기능 목적/흐름도를 사용자와 합의
2. **구현**
3. **버그 가능성 테스트** — 흔한 실수·엣지 케이스를 검증하는 테스트 작성
4. **PR 전, §6의 적대적 검증 절차를 최소 1회 수행**

### B. 버그 수정 (TDD)
1. **버그 리포트 확인**
2. **코드 수정 전에** 버그를 재현하는, 반드시 실패하는 테스트를 먼저 작성
3. 그 테스트가 통과하도록 메인 코드 수정
4. **이 순서(재현 테스트 → 수정)를 절대 건너뛰지 마라**

### C. 백그라운드(IO-bound) 작업 추가
1. 화면 그리기 로직과 완전히 분리해 백그라운드로 실행
2. 상태 머신으로 감시
3. 상태 변화 시 이벤트 emit
4. UI는 루프 주기마다 이벤트를 소비하고 갱신

## 6. 컨텍스트 없는 서브 에이전트를 통한 적대적 검증 (구체화)

당신은 사용자와의 긴 대화(컨텍스트)에 갇혀 스스로의 코드 맹점을 못 볼 수 있다는 것을 항상 인지하라.  
아래는 §5-A-4, §5-B-4에서 요구하는 "적대적 검증"을 실제로 수행하는 절차다.

### 6.1 호출 시점 (하나라도 해당하면 반드시 수행)
- 새 기능 구현을 완료하고 PR을 올리기 직전
- 상태 머신/비동기/이벤트 로직처럼 동시성이 관련된 코드를 수정했을 때
- 버그를 수정한 직후 (재발 방지 확인 차원)
- 사용자가 명시적으로 요청했을 때
- 그 외에도, 변경 규모가 일정 수준 이상이면 주기적으로
- **[반복 검증 원칙]** 동시성 결함을 고치기 위해 새로운 방어 장치(락, 플래그, 큐, 디스패처 등)를 도입한 경우, 그 수정을 "검증 완료된 안전한 코드"로 간주하지 말고 **그 수정 코드 자체를 대상으로 다시 한 번 검증 라운드를 수행하라.** 동시성 버그 수정 코드는 새로운 동시성 버그가 태어나는 가장 흔한 자리다. "이상 없음"이 나올 때까지, 혹은 더 이상 새 결함이 나오지 않을 때까지 이 라운드를 반복하라.

### 6.2 호출 방법
- 별도의 새 대화/세션(또는 컨텍스트가 분리된 서브 에이전트)으로 호출하고, **지금까지의 대화 맥락(이전 논의, 의도, 배경)은 절대 전달하지 마라.**
- 서브 에이전트에게는 오직 다음 2가지만 전달하라:
  1. **대상 코드/설계 diff**
  2. [AI_ADVERSARIAL_VALIDATOR_GUIDE.md](file:///c:/Users/%EC%9D%B4%ED%99%8D%EC%9B%90/Desktop/code_training/chzzk_downloader/docs/AI_ADVERSARIAL_VALIDATOR_GUIDE.md) 원문 전문 (시스템 프롬프트)
- **당신이 왜 이 코드를 이렇게 짰는지 설명하거나 정당화하지 마라 — 그 순간 검증이 아니라 변명이 된다.**

### 6.3 서브 에이전트에게 전달할 시스템 프롬프트
- [AI_ADVERSARIAL_VALIDATOR_GUIDE.md](file:///c:/Users/%EC%9D%B4%ED%99%8D%EC%9B%90/Desktop/code_training/chzzk_downloader/docs/AI_ADVERSARIAL_VALIDATOR_GUIDE.md) 파일 내용을 그대로 복사하거나 주입하여 사용한다.

### 6.4 결과 처리
- 서브 에이전트가 제시한 재현 코드를 **그대로 신뢰하지 마라.** 서브 에이전트 역시 §4에서 경계하는 "가짜 성공"과 대칭적인 "가짜 검증(그럴듯한 실행 결과를 실제로 돌려보지 않고 서술)"을 할 수 있는 동일한 리스크를 갖는다. 보고서의 "재현 확인 방식"이 정적 분석(미실행)으로 표시되어 있다면, **반드시 실제 코드베이스에서 직접 실행해 보고된 실패가 재현됨을 확인한 뒤에만 다음 단계로 넘어가라.**
- 재현이 실제로 확인된 지적만 §5-B의 TDD 워크플로우(재현 테스트 먼저 → 수정)로 처리하라.
- 근거 없거나 재현 불가능한 지적은 그 이유를 명시해 기각해도 된다. 무조건 수용하지 마라.
- G(네이밍) 지적은 버그 수정과 분리해 별도 개선 항목으로만 반영하라.
- 보고서의 "개선 우선순위 및 근본 원인 매핑"을 존중하라: P0 항목을 먼저 처리하고, 공통 근본 원인으로 묶인 결함은 최소 수정 집합으로 한 번에 해소되는지 확인한 뒤 수정 순서를 정하라.
- **수정을 적용한 뒤에는 §6.1의 반복 검증 원칙에 따라 그 수정 코드를 대상으로 검증 라운드를 다시 요청하라.** 특히 동시성 방어 장치(락, 플래그, 큐 등)를 새로 추가했다면 예외 없이 재검증하라 — 이 코드가 다음 라운드의 결함 소스가 되는 경우가 흔하다. "이상 없음"이 나오거나 새로 발견되는 결함이 더 이상 크리티컬하지 않을 때까지 이 사이클을 반복하라.

## 9. 세션 종료 시 인계 정보 출력 (다음 세션 핸드오프)

이 프로젝트는 세션마다 컨텍스트가 초기화되고, 다음 세션은 이 지침 프롬프트만 다시 주입받아 새로 시작한다. 따라서 과업을 마칠 때 다음 세션이 그대로 이어받을 수 있는 인계 정보를 반드시 출력하라.

**핵심 원칙 (확률 통제):**  
인계 정보는 당신의 대화 기억이나 인상에 의존해 확률적으로 재구성하지 마라. "아마 이 파일도 건드렸을 것"과 같은 추측성 서술은 절대 포함하지 마라. 반드시 실제 명령을 실행해 얻은 **결정적(deterministic) 사실**만 담아라. 이는 §4·§6.4에서 요구한 "가짜 검증 금지" 원칙을 세션 인계에도 동일하게 적용하는 것이다 — 잘못된 파일 목록 위에서 다음 세션이 출발하면 그 세션 전체가 틀어진다.

### 9.1 출력 시점
- 부여된 과업이 완료되었다고 판단될 때
- 사용자가 세션 종료를 언급할 때
- 사용자가 "인계 정보 / 핸드오프 / 세션 요약"을 요청할 때

### 9.2 파일 목록은 반드시 도구 실행 결과로 산출하라
- 버전 관리 중이라면 `git status --porcelain`과 `git diff --name-status HEAD`(또는 이번 세션 시작 커밋 대비 diff)를 실행해 실제 변경된 파일과 변경 종류(추가/수정/삭제)를 얻어라.
- 버전 관리가 없다면 세션 시작 시점과 종료 시점의 디렉터리 상태(`find`, `ls -la`, `Get-ChildItem` 등)를 비교해 변경분을 산출하라.
- 명령 실행 결과를 그대로, 혹은 최소한의 정리만 거쳐 인계 정보에 포함하라. **실행 결과에 없는 파일을 추가하거나, 실행 결과에 있는 파일을 빠뜨리지 마라.**
- 참조만 하고 수정하지 않은 파일(예: 읽기만 한 설계 문서)도 다음 세션이 알아야 한다면 별도로 "참조한 파일" 목록을 만들되, 이것도 실제 view/read 이력에 근거해야 하며 기억으로 재구성하지 마라.

### 9.3 인계 정보 표준 포맷 (다음 세션 전달용)

다음 형식으로 출력하라 (다음 세션 시작 시 그대로 붙여 넣을 수 있도록):

```markdown
## 세션 인계 정보 (Handoff)

### 1. 이번 세션에서 변경된 파일 (git diff --name-status 실행 결과 원문)
<명령 실행 결과를 그대로 붙여넣음>

### 2. 이번 세션에서 참조만 한 파일 (수정 없음, view/read 이력 기준)
- path/to/file: 참조 목적 한 줄

### 3. 파일별 변경 요약 (diff 내용에 근거, 추측 금지)
- path/to/file.py: 한 줄 요약

### 4. 검증 상태 (실제 실행 결과 기준)
- 실행한 테스트 명령과 통과/실패 개수
- 이번 세션에서 수행한 적대적 검증(§6) 라운드 횟수와 최종 결과(이상 없음 / 남은 결함)

### 5. 미해결·이월 항목 (다음 세션이 이어서 할 것)
- ...

### 6. 다음 세션 착수 시 먼저 읽어야 할 파일 (우선순위 순)
- ...
```

### 9.4 불확실한 항목의 처리
- 명령 실행으로 확인되지 않은 내용은 인계 정보에 확정형으로 쓰지 말고 "확인 필요"로 표시하라. 확인 필요 항목을 그대로 다음 세션에 넘기는 것이, 확인 없이 그럴듯하게 서술해 넘기는 것보다 낫다.

## 10. 용어 사전 (Nomenclature)

- **컨텍스트 (Context):** AI와 대화하면서 쌓인 '맥락'이나 '배경지식'. "컨텍스트 없는 에이전트"란 지금까지 뭘 만들고 있었는지 전혀 모르는 백지상태의 새로운 AI를 뜻함.
- **적대적 검증 (Adversarial Validation):** 코드가 잘 돌아가는지 확인하는 게 아니라, "어떻게든 이 코드를 망가뜨려 보겠다"는 목적으로 약점을 공격하고 검사하는 방법.
- **CPU 바운드 / IO 바운드:**
  - CPU 바운드: 복잡한 수학 계산처럼 CPU를 100% 혹사시키는 작업.
  - IO 바운드: 파일 다운로드, 응답 대기처럼 CPU는 노는데 "기다리는 시간"이 많은 작업. GUI에서는 이 때문에 화면이 자주 멈춤.
- **비동기 (Asynchronous) / 병렬화 (Parallelism):** 앞의 작업이 끝날 때까지 기다리지 않고 다른 일을 먼저 처리하거나(비동기), 여러 작업을 동시에 시키는(병렬화) 기법. 대기 시간을 줄이기 위해 씀.
- **상태 머신 (State Machine):** 프로그램이 현재 어떤 상태인지(대기 중 → 설치 중 → 완료/실패)를 엄격히 정의하고, 조건이 맞을 때만 다음 상태로 넘어가게 통제하는 시스템.
- **시그널 슬롯 (Signal & Slot) / 이벤트:** 특정 사건이 발생하면 방송(시그널/이벤트)을 하고, 기다리던 쪽(슬롯)이 특정 행동을 하도록 연결하는 통신 방식.
- **모킹 (Mocking):** 테스트 시 실제 데이터 대신 가짜 데이터/상황을 만들어 정답처럼 꾸미는 행위. AI가 테스트를 쉽게 통과하려고 남용하는 것을 경계해야 함.
- **원자성 (Atomicity):** 여러 단계로 이루어진 작업(예: 자원 반환 + 다음 작업 할당)이 "전부 실행되거나 전혀 실행되지 않은 것처럼" 하나의 끊기지 않는 단위로 처리되는 성질. 중간에 락이 풀려 다른 작업이 끼어들 수 있으면 원자성이 깨진 것임.
- **멱등성 (Idempotency):** 같은 요청을 한 번 보내든 여러 번 보내든 결과가 동일하게 유지되는 성질. 멱등성이 없으면 중복 클릭이나 재요청만으로 내부 상태가 오염될 수 있음.
- **캡슐화 (Encapsulation):** 내부 구현 세부사항(private 멤버 등)을 외부에 감추고, 정해진 공개 인터페이스로만 상호작용하게 만드는 설계 원칙. 외부 코드가 `_`로 시작하는 내부 변수를 직접 건드려야만 동작한다면 캡슐화가 깨진 것임.
- **재진입성 (Reentrancy) vs 스레드 세이프티 (Thread-safety):** 서로 다른 개념임. 재진입성은 "같은 스레드가 실행 도중 같은 함수를 다시 호출해도 안전한가"를 다루고(예: 재귀 캐스케이드 방지), 스레드 세이프티는 "여러 스레드가 동시에 같은 자원에 접근해도 안전한가"를 다룸. 단일 스레드 재진입만 막도록 짠 플래그나 큐는, 여러 스레드가 동시에 그 플래그·큐 자체에 접근하는 상황에서는 아무 보호도 해주지 못함 — 이 둘을 혼동하면 "고쳤다고 생각한 버그"가 다른 얼굴로 재발함.
